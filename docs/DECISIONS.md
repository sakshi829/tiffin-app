# Technical decisions log

Business decisions are in [PLAN.md](../PLAN.md) section 2. This file records implementation choices.

| # | Date | Decision | Why |
|---|---|---|---|
| T1 | 2026-11-21 | Tables in `public` with RLS; helpers in private `app` schema (not exposed by the API) | Standard Supabase pattern (works with Realtime); helpers callable only from SQL |
| T2 | 2026-11-21 | Customers/staff have **no** direct write grants; all their writes go through `customer_*` / `staff_*` functions | Ownership, cutoff and input checks happen in one audited place; closes IDOR and payload tampering |
| T3 | 2026-11-21 | Owner writes config tables directly (column-level grants + RLS); orders, money, prices, staff, invites, subscriptions only via functions | Simple CRUD where safe; strict paths where money or access is affected |
| T4 | 2026-11-21 | Composite foreign keys `(id, kitchen_id)` everywhere | The database itself makes cross-kitchen references impossible, independent of RLS |
| T5 | 2026-11-21 | Ledger, audit log, bills, box movements are append-only via triggers (even the DB owner cannot edit) | Money history can never be silently rewritten; corrections are reversal entries |
| T6 | 2026-11-21 | Charges are created on status transitions under row locks (delivered, late skip); corrections = reverse all, then re-apply | Exactly-once charging without fragile unique indexes; ledger always matches order state |
| T7 | 2026-11-21 | Prices snapshot on orders; price changes re-price only orders **before their cutoff** | Kitchen planning stays stable; customers see new prices from the effective date |
| T8 | 2026-11-21 | Server clock via `app.now()` (tests replace it); cutoffs computed in Asia/Kolkata | Phone clock changes have no effect; time logic is testable |
| T9 | 2026-11-21 | Invite codes: 10 chars from a 31-char alphabet (~49.5 bits), stored as SHA-256, single use, expiring, 5 failures/hour lockout; failures return a value (not an exception) so the lockout counter is committed | Brute force is impractical; a raised error would roll back the counter |
| T10 | 2026-11-21 | Step-up = TOTP verified within 10 minutes (`amr` claim) for prices, staff, unlink, waivers, settings | A stolen, already-open owner session cannot change money rules without the authenticator |
| T11 | 2026-11-21 | Audit stores only changed columns; bulk order inserts and customer location updates are not audited (they are on the order row) | Keeps the 500 MB free database small (~tens of MB/year) |
| T12 | 2026-11-21 | Database tests use PGlite (Postgres in WASM) + a Supabase shim instead of pgTAP/Docker | Runs anywhere with Node (no Docker); same SQL; shim reproduces Supabase's permissive defaults so tests prove we remove them. `verify_live.sql` re-checks on the real project |
| T13 | 2026-11-21 | Phase 1 contains the tables needed by Phases 2–3b; engagement tables (chat, voice notes, special menus, loyalty, ingredients, waste, budgets, join/referral requests, staff shifts) are added in their own phases, each with RLS + tests | Avoids untested schema; every table ships with its security tests (PLAN.md section 19 rule) |
| T14 | 2026-11-21 | Backups: data-only `pg_dump` (schema is in git), encrypted with `age` public key, kept as private 90-day workflow artifacts | Free; private key never on GitHub; restore = migrations + data |
| T15 | 2026-11-21 | Own small UI kit (`apps/owner/src/ui`) instead of React Native Paper (PLAN.md section 4) | Paper's compatibility with React Native 0.88 / React 19.3 is unverified; a dozen plain components cover the needs with no extra dependency. 48 px touch targets, light/dark, accessibility roles |
| T16 | 2026-11-21 | No react-hook-form; plain state + validation, with the database re-validating everything | Forms are short; one less dependency. The database is the real validator |
| T17 | 2026-11-21 | i18n: user-facing **error messages** are centralised in `packages/shared/src/errors.ts`; screen labels are inline English until Phase 8 | Marathi/Hindi is Phase 8; centralising errors now (with a test that every DB code has a message) avoids gaps |
| T18 | 2026-11-21 | Owner sign-in = email 6-digit code with `shouldCreateUser: false`, then mandatory TOTP. No Google sign-in for the owner app yet | No Google Cloud setup needed to start; the owner app can never create accounts; MFA covers the email risk |
| T19 | 2026-11-21 | Screens that need joined data use tested `owner_*` report functions (`1100_owner_reports.sql`) instead of PostgREST resource embedding | Our composite foreign keys make embedding behaviour uncertain, and functions are testable on PGlite |
| T20 | 2026-11-21 | API contract (`packages/shared/src/api-contract.ts`) checked by `11-api-contract.test.mjs`; the app's `rpc()` also rejects mismatched arguments | Catches app/schema drift in CI without a running backend |
| T21 | 2026-11-21 | Session storage: Supabase's `LargeSecureStore` pattern on phones (AES-256 key in SecureStore, ciphertext in AsyncStorage); default localStorage on web | Follows Supabase's Expo guide; SecureStore alone may reject large values |
| T22 | 2026-11-21 | Step-up AMR names `totp` and `mfa/totp` accepted; anything else (string format, malformed, older than 10 min) fails closed | auth-js types list both names; Supabase issues the timestamped object format unless custom hooks are used |
| T23 | 2026-11-21 | App lock overlays the app (2 min background / launch with a saved session); no lock right after a fresh sign-in | Keeps navigation state; avoids double authentication |
| T24 | 2026-11-21 | Tabs from `expo-router/js-tabs` (the root `Tabs` export is deprecated in SDK 58); auth gating with `Stack.Protected` on one `(app)` group | Verified against the installed expo-router 58.0.32 type definitions; one protected group means no screen can be reached by accident |

| T29 | 2026-11-21 | Confirmations are inline cards, not `Alert.alert` | `Alert.alert` is not functional on web (react-native-web), and the customer app must work as an iPhone web app |
